**Date:** 2026-04-11 08:06

**Scope:** Fix three broken developer experience gaps discovered during codebase audit:

## Codebase Intelligence

### Project Structure

Single-package repository. One publishable npm package (`opencode-nudge/`) plus workspace-level OpenCode configuration (`.opencode/`), GitHub Actions CI (`.github/workflows/`), and a root `Makefile` that orchestrates all developer operations.

```
opencode-aware/
├── opencode-nudge/       # npm package: TypeScript source, tests, dist/
├── .opencode/            # OpenCode workspace config (plugin registration, commands, agents)
├── .github/workflows/    # Five GitHub Actions workflows (all OpenCode-agent-driven)
├── .agents/plans/        # Implementation plan artifacts
├── docs/                 # Developer reference docs
├── Makefile              # Root orchestrator for all make targets
└── .gitignore
```

**Build system:** `Makefile` (root) + `bunx tsc` (TypeScript compilation via `tsconfig.build.json`).  
**Package manager:** Bun for development; npm for publishing.

### Conventions

- **Naming:** `kebab-case.ts` source files; `*.test.ts` for tests co-located in `src/`; `SCREAMING_SNAKE_CASE` constants; `camelCase` functions; `PascalCase` types/exports
- **Module organization:** `types.ts` → `throttle.ts` → `idle-handler.ts` → `index.ts` (strict layering, no reverse imports)
- **Test patterns:** `bun:test`, `describe`/`it`, hand-crafted minimal mocks via `mock()`, `sessionStates.clear()` in `beforeEach`, env isolation in `beforeEach`/`afterEach`
- **Config patterns:** Single env var `OPENCODE_IDLE_THRESHOLD_MS` via `process.env["KEY"]` bracket notation; no `.env` files; OpenCode config in `.opencode/opencode.jsonc`
- **Import paths:** `.js` extensions required on all project-relative imports (ESM + Bun requirement)

### Reusable Abstractions

- `log(client, level, message, extra?)` — private helper in `idle-handler.ts`, all production logging must use this
- `getOrCreateState` / `canContinue` / `recordContinuation` — pure rate-limit API in `throttle.ts`
- `getIdleThreshold()` — env-overridable constant accessor in `types.ts`
- `makeClient()` factory in test files — minimal mock pattern for new tests

### Tooling Constraints

- `strict: true` TypeScript — no `any` in production code
- `"moduleResolution": "bundler"` — do not change
- No ESLint/Prettier — `make lint` = `make typecheck`
- `make validate` = `make lint` + `make test` — the canonical pre-merge gate
- All CI uses `ubuntu-latest` GitHub Actions runners
- `make test-e2e` requires a live AI provider — not suitable for standard CI

### Patterns to Avoid

- `console.log` — swallowed by OpenCode; use `client.app.log()` via the `log()` helper
- Absolute paths that depend on the developer's local filesystem layout in committed config files
- Direct `sessionStates` Map mutation outside `throttle.ts`
- `any` in production source files

### Step 2: Create the Missing `hooks/pre-push` File

**Owner:** Coding subagent

**Objective:**  
Create the `hooks/pre-push` shell script that `make install` configures git to use. Without this file, `make install` fails at `chmod +x hooks/pre-push` with a "No such file or directory" error, making the full developer setup broken.

**Why it is needed:**  
The pre-push hook is the last line of defence before code reaches the remote. It catches type errors and unit test failures that might slip through in-editor tooling. Its absence means the hook infrastructure is wired up in the `Makefile` but has no content — any developer running `make install` will see an error.

**Dependencies:**
- Step 0 (Workbench Setup) must be complete.

**Scope of work:**
- New file: `hooks/pre-push` (executable shell script)
- No changes to `Makefile` (it already references `hooks/pre-push` correctly)

**Task breakdown:**

1. Create the `hooks/` directory at the repository root if it does not already exist.
2. Create `hooks/pre-push` as a POSIX shell script that:
   - Runs `make validate` (= `make typecheck` + `make test`)
   - Exits non-zero on any failure, blocking the push
   - Prints a clear message on failure
3. Make the file executable: `chmod +x hooks/pre-push`.
4. Run `make install` to confirm it completes without error.
5. Verify the hook is invoked by simulating a push (or by calling the hook directly).

**Code changes to apply:**

Create `hooks/pre-push`:

```sh
#!/bin/sh
# Pre-push hook: runs typecheck + unit tests before every push.
# Blocks the push if any check fails.

set -e

echo "Running pre-push checks..."
make validate

echo "Pre-push checks passed."
```

Make executable:
```bash
chmod +x hooks/pre-push
```

**Verification:**

```bash
# Test the hook directly
./hooks/pre-push
# Expected: "Pre-push checks passed."

# Test make install completes
make install
# Expected: no errors, git hook path configured
git config core.hooksPath
# Expected: hooks
```

**Validation:**

- `./hooks/pre-push` runs `make validate` and exits 0 when tests pass.
- If `make validate` would fail, the hook exits non-zero.
- `make install` completes successfully end-to-end.
- Hook file is committed and tracked by git.

**Acceptance criteria:**

- `ls -la hooks/pre-push` shows an executable file.
- `./hooks/pre-push` exits 0 on a clean codebase.
- `make install` exits 0 with no errors.

**Definition of done:**

- `hooks/pre-push` committed and executable.
- `make install` verified to complete successfully.
- Hook script documented as minimal — no `--no-verify` bypass paths.

**Known gotchas:**

- `set -e` causes the script to exit on the first failing command, which is the desired behaviour for a blocking hook.
- The hook must be a POSIX shell script (`#!/bin/sh`), not bash-specific (`#!/bin/bash`), for maximum portability across CI and developer machines.
- `make test-e2e` is intentionally excluded from the pre-push hook (it requires a live AI provider and takes ~20 seconds). The hook only runs unit-level validation.
- Git hooks are not executed when using `--no-verify` flag. The hook guards against accidental pushes, not malicious bypasses.
- The file must be tracked by git (not gitignored). Confirm `.gitignore` does not have a `hooks/` or `hooks/pre-push` exclusion pattern.

**Outputs for orchestrator:**

- New file: `hooks/pre-push`
- Confirmation that `make install` runs cleanly

### Step 3: Add a CI Validate Workflow

**Owner:** Coding subagent

**Objective:**  
Add a GitHub Actions workflow that runs `make validate` (typecheck + unit tests) on every push and pull request. Currently, zero automated quality gates exist in CI — all five workflows are OpenCode-agent-driven and never run `bun install`, `make typecheck`, or `make test`.

**Why it is needed:**  
Type errors and failing unit tests are only caught locally via the pre-push hook (now restored in Step 2). If someone bypasses the hook (`--no-verify`) or pushes from an environment where hooks are not installed, broken code reaches the remote undetected. A CI validate workflow provides the safety net.

**Dependencies:**
- Step 0 (Workbench Setup) must be complete.
- Step 2 should be complete first (hooks + validate target confirmed working) — but this step can be executed in parallel if the subagent independently verifies `make validate` runs cleanly.

**Scope of work:**
- New file: `.github/workflows/validate.yml`
- No changes to existing workflows

**Task breakdown:**

1. Create `.github/workflows/validate.yml`.
2. Trigger on: `push` (all branches) and `pull_request`.
3. Use `ubuntu-latest` runner (matches existing CI convention).
4. Steps:
   a. `actions/checkout@v5` (matches existing workflows)
   b. `oven-sh/setup-bun@v2` — install Bun
   c. `bun install --frozen-lockfile` in `opencode-nudge/` — install dependencies, fail fast if lockfile is stale
   d. `make validate` — typecheck + unit tests
5. Do NOT include `setup-uv` (Python toolchain — not needed for this project).
6. Do NOT include `make test-e2e` (requires a live AI provider).
7. Keep the workflow minimal: one job, four steps.

**Code changes to apply:**

Create `.github/workflows/validate.yml`:

```yaml
name: Validate

on:
  push:
  pull_request:

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5

      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: latest

      - name: Install dependencies
        run: bun install --frozen-lockfile
        working-directory: opencode-nudge

      - name: Typecheck and test
        run: make validate
```

**Verification:**

# Expected: typecheck pass + 18/18 unit tests pass

**Validation:**

- `on: push` and `on: pull_request` triggers are both present.
- No `setup-uv` step (absent = correct).
- `bun install --frozen-lockfile` guards against stale lockfiles.
- `make validate` is the single quality gate command (not duplicating individual steps).
- Workflow name `Validate` is concise and distinct from existing workflow names.

**Acceptance criteria:**

### Step E2E (Always-Append Penultimate): Adversarial End-to-End Validation

**Owner:** General-purpose testing subagent (CLI testing capability required — this plan involves `make` targets, shell hooks, and a locally-built TypeScript plugin)

**Mandate (verbatim):**

Execute the main user journey exactly as a real user would — from entry point to final outcome — against a real environment with real data. Cover the full happy path first, then systematically attack it: invalid inputs, missing permissions, network failures, empty states, concurrent access, boundary values, and any edge case implied by the spec. Every warning, error, deprecation notice, console output, slow query, or unexpected behavior must be logged and reported. Nothing is suppressed or explained away. If anything does not work as specified, the step is **FAILED**. Fix the root cause and re-run from the start of this step. Do not patch symptoms. Reach for the highest possible bar: if the feature can be made more correct, more robust, or more performant within scope, do it and re-validate. Report results as binary: ✅ WORKING or ❌ BROKEN. No partial credit. No "mostly works".

**An E2E test is only complete when all of the following are true in a single uninterrupted execution:**

1. **Real system running** — the system under test is started in its production-equivalent configuration; no component is replaced by a stub, mock, or simplified harness
2. **Real entry point** — the triggering condition is produced through the same entry point a real user or upstream system would use; nothing is injected mid-stack or via an internal API that bypasses the front door
3. **Full code path traversed** — the system's own code handles the trigger from entry to exit; this is confirmed by the system's own observable output (logs, UI state, persisted data), not inferred from prior unit or integration tests
4. **No layer substituted** — every layer between the trigger and the expected effect participates in the same run; manually calling a downstream function directly to "simulate" a layer does not count
5. **Side-effect verified externally** — the expected outcome is confirmed the way a real end user would confirm it (visible output, file written, message sent, UI updated); internal assertions alone are not sufficient

**Partial satisfaction is failure.** Meeting four out of five conditions, or meeting all five across separate runs, is the same as not having an E2E test at all.

**E2E test mindset (verbatim):**

- The goal is to delight the user, not to ship something that appears to work
- This step exists to surface every surprise before the user encounters it. No mocking. No shortcuts. No fingers crossed.
- Assume everything needed is already prepared for execution (credentials set up, tools installed etc.)
- If that assumption is wrong, execute the test anyway and record the failure.
- Define the test first, boldly, from the outside in.
- Run the real test, not a mocked or protected version.
- Do not avoid painful paths; target them.
- Do not substitute caution for execution.
- Surface failures immediately, clearly, and loudly.
